# 순위 추적 페이지 리디자인 설계 스펙

**작성일:** 2026-07-08
**범위:** `client/src/pages/RankTrackerPage.jsx`(및 신설 하위 컴포넌트)의 레이아웃/디자인 전면 교체. 데이터 흐름·API 계약·백엔드 순위 갱신 로직은 변경하지 않는다(단, 목록 조회 API 응답에 필드 2개 추가 — 아래 8절).
**적용 대상:** 순위 추적 기능을 쓰는 모든 사용자 (기존 프리미엄 게이트 유지).

---

## 1. 배경 및 문제

현재 순위 추적 페이지는 인라인 스타일을 그때그때 즉흥적으로 섞어 써서, 이 앱의 나머지 부분(`styles.css`의 "macOS Sequoia" 디자인 시스템 — `.mac-card`, `.mac-table`, `.mac-badge`, `.mac-btn` 등, `SummaryCards.jsx` 같은 통계 카드 패턴)과 톤이 안 맞는다. 버튼이 줄바꿈되며 뒤죽박죽 배치되고, 왼쪽 300px 카드 리스트 + 오른쪽 상세 패널 구조라 카드 안에서 정보가 세로로 계속 쌓여 한눈에 비교가 안 된다. 반면 엑셀 내보내기는 표 형태로 열이 맞춰져 있어 파악이 쉽다는 피드백을 받았다.

이번 리디자인의 목표는 두 가지다.
1. **화면에서도 엑셀만큼 한눈에 파악되게** — 카드 리스트 대신 정렬 가능한 테이블 기반 레이아웃으로 전환.
2. **"AI가 급조한 것 같지 않게"** — 새로운 스타일을 발명하지 않고, 이 앱에 이미 있는 검증된 디자인 시스템과 컴포넌트 패턴을 일관되게 재사용한다.

브라우저 기반 시각 자료로 사용자와 두 차례 목업을 검토해 아래 방향으로 합의했다.

---

## 2. 페이지 구조 (위→아래)

1. 모드 탭 (블로그 추적 모드 / 전체 순위 모드) — 기존 유지, 스타일만 정리
2. **요약 통계 카드 4개** (신설)
3. **툴바** — 왼쪽: 그룹 필터 + 키워드 검색, 오른쪽: 액션 버튼들
4. **테이블** — 정렬 가능한 헤더, 키워드+블로그 조합당 한 행
5. 행 클릭 시 **오버레이 드로워**(화면 오른쪽에서 슬라이드, 배경은 반투명 스크림)로 순위 추이 차트 + 캘린더 히트맵 표시

기존의 "300px 사이드바 + 오른쪽 상세 패널" 2단 구조는 폐기한다. 테이블이 항상 전체 폭을 쓴다.

---

## 3. 요약 통계 카드

`SummaryCards.jsx`와 동일한 시각 패턴(아이콘 배지 우상단 + 큰 숫자 + 하단 보조 텍스트/진행바, 카드 상단에 색상 테두리 한 줄 + 옅은 radial-gradient 틴트)을 그대로 재사용한다. 4개 카드:

| 카드 | 값 | 보조 표시 |
|---|---|---|
| 추적 키워드 | 필터링된 키워드 개수 | "그룹 N개에 분산" |
| 추적 링크 | 필터링된 블로그 링크 총합 | "키워드당 평균 X개" |
| 5위 내 노출 | 5위 이내 노출 중인 링크 수 / 전체 링크 수 | 진행바 |
| 통검 노출 중 | 통합검색 노출 중인 링크 수 / 전체 링크 수 | 진행바 |

**중요**: 이 4개 값은 전부 현재 화면에 적용된 필터(그룹 선택 + 키워드 검색, 즉 기존 `filteredItems`)를 기준으로 계산한다. 그룹을 바꾸거나 검색어를 입력하면 카드 숫자도 즉시 그 필터 기준으로 다시 계산된다.

"최근 갱신" 시각은 카드로 승격하지 않고, 기존처럼 툴바 근처에 작은 텍스트로만 남긴다(이미 구현되어 있는 `최근 갱신: {formatKSTDateTime(...)}` 로직 그대로 재사용).

"전체 순위 모드"(all)에는 블로그 단위 개념이 없으므로 "추적 링크"/"통검 노출 중" 카드는 이 모드에서 의미가 없다 — all 모드에서는 "추적 키워드"와 "5위 내 노출"(최신 스냅샷 중 상위 5위 이내로 재정의) 2개 카드만 렌더링하고, 그리드는 2칸으로 줄인다(빈 카드 자리를 만들지 않음).

---

## 4. 툴바

한 줄, flex 배치. 왼쪽부터: 그룹 선택 드롭다운 → 키워드 검색 입력 → (spacer) → 전체 갱신 → 내보내기 → 대량 등록 → 등록(accent 버튼, 맨 오른쪽 고정). "전체 삭제"/"선택 삭제"는 상시 노출 버튼에서 빼고, 테이블 헤더의 체크박스 옆에 선택된 개수가 있을 때만 나타나는 보조 액션으로 옮긴다(선택 안 했는데 "전체 삭제" 버튼이 항상 떠 있는 건 위험하고 혼란스럽다 — 이 부분은 리디자인하면서 같이 개선).

버튼 스타일은 `.mac-btn` / `.mac-btn-ghost` / `.mac-btn-sm` 클래스를 그대로 쓴다(새 버튼 스타일 발명 안 함).

---

## 5. 테이블

**행 단위**: 키워드+블로그 조합마다 한 행 (엑셀 내보내기와 동일한 단위).

**컬럼**: 체크박스 | 키워드(그룹 배지 포함, 정렬 가능) | 블로그 | 검색량(정렬 가능) | 순위(정렬 가능, 최신 순위) | 통검노출(O/X) | 행 액션(블로그 추가 +, 블로그 제거 ✕, 키워드 삭제 🗑)

**같은 키워드의 여러 블로그 그룹핑**: 같은 키워드에 속한 첫 번째 행에만 키워드 텍스트·그룹 배지·체크박스·행 액션(추가/삭제)을 표시한다. 같은 키워드의 나머지 블로그 행은 키워드 칸을 비우고(살짝 들여쓰기 + 옅은 배경으로 시각적으로 묶여있음을 표시) 블로그별 값(블로그ID/검색량 없음/순위/통검노출)만 보여준다. 키워드 그룹 사이는 위쪽 테두리를 굵게 줘서 구분한다.

**정렬**: 키워드/검색량/순위 헤더 클릭 시 오름차순↔내림차순 토글. 기본 정렬은 API가 주는 순서(등록 최신순)를 그대로 유지 — 별도로 강제하지 않는다.

**체크박스/선택 삭제**: 키워드 단위로 동작(첫 번째 행에만 체크박스). 같은 키워드의 블로그 행 전체가 함께 선택/삭제된다. 기존 `handleBulkDelete`/`selectedIds` 로직 그대로 재사용.

**스타일**: `.mac-table` 클래스 기반. sticky 헤더, hover 시 행 배경 변경 등 기존 `.mac-table` 스타일 그대로 활용.

## 6. 오버레이 드로워 (상세 보기)

행(키워드 그룹) 클릭 시 화면 오른쪽에서 슬라이드-인하는 드로워. 배경에는 반투명 스크림(클릭하면 닫힘). 드로워 폭은 데스크톱 기준 화면의 약 40~45%.

드로워 내용은 기존 상세 패널의 내용을 그대로 옮긴다 — 변경 없음:
- 키워드명 + 블로그 개수
- 마지막 갱신 시각 + 개별 갱신 버튼
- `RankChart`(순위 추이 차트)
- `RankCalendar`(캘린더 히트맵)
- 블로그별 최신 순위 리스트

닫기는 ✕ 버튼 또는 스크림 클릭 또는 ESC 키.

"전체 순위 모드"(all)의 드로워는 기존처럼 최신 스냅샷의 상위 10개 리스트를 보여준다(변경 없음, 컨테이너만 오버레이 드로워로 이동).

## 7. 컴포넌트 분리

`RankTrackerPage.jsx`가 1300줄이 넘어 이번에 렌더링을 통째로 새로 짜는 김에 아래로 쪼갠다. `RankTrackerPage.jsx`는 데이터 페칭·상태·이벤트 핸들러(이미 존재하는 `loadItems`, `handleRefresh`, `handleDelete` 등)만 담당하고, 아래 컴포넌트들을 조합해 렌더링한다.

- `client/src/components/rankTracker/TrackerStatCards.jsx` — 3절의 통계 카드 4개. `filteredItems` + `groups`를 받아 자체적으로 집계.
- `client/src/components/rankTracker/TrackerToolbar.jsx` — 4절의 툴바. 그룹/검색 상태와 각 액션 콜백을 props로 받는 순수 프레젠테이션 컴포넌트.
- `client/src/components/rankTracker/TrackerTable.jsx` — 5절의 테이블. `filteredItems` + 정렬 상태 + 선택 상태 + 행 클릭/액션 콜백을 props로 받음.
- `client/src/components/rankTracker/TrackerDetailDrawer.jsx` — 6절의 드로워. `selected`/`snapshots`/열림 여부를 props로 받고, 기존 `RankChart`/`RankCalendar`를 그대로 사용.

각 컴포넌트는 자기 데이터를 직접 fetch하지 않고 props로만 받는다(테스트/이해가 쉬운 순수 프레젠테이션 컴포넌트 유지).

## 8. 백엔드 변경

`server/services/rankTrackerService.js`의 `listTracked(userId)`가 현재 검색량(`pc_search`/`mobile_search`)과 통합검색 노출 여부를 반환하지 않는다(지금은 엑셀 내보내기용 `exportSnapshots`에서만 조회). 테이블의 검색량 컬럼과 통검노출 컬럼/KPI 카드를 위해 두 가지를 추가한다.

- `listTracked`의 `tracked_keywords` SELECT에 `pc_search, mobile_search` 추가.
- 각 항목의 최신 스냅샷 조회 쿼리(`rank_snapshots`)에 `integrated_exposed` 컬럼을 추가하고, `latestByBlog[blogId]`에 `integratedExposed` 필드로 포함(모드가 'blog'일 때만 의미 있음, 'all' 모드는 null로 둠 — `exportSnapshots`의 기존 처리 방식과 동일).
- 응답 형태에 `searchVolume`(pc_search+mobile_search 합산, 둘 다 null이면 null) 필드 추가.

기존 `exportSnapshots`/`refreshRanks`/그 외 순위 갱신·저장 로직은 변경하지 않는다.

## 9. 유지되는 것

- 그룹 관리(생성/이름변경/삭제/이동), 대량 등록 모달, 전체 갱신(잡 기반), 실패 재시도, 엑셀 내보내기 — 전부 기존 로직 그대로, 진입점(버튼) 위치만 툴바로 재배치.
- API 계약(엔드포인트/요청·응답 형식)은 8절에서 언급한 목록 조회 응답 필드 추가 외에는 변경 없음.
- 프리미엄 게이트, 로그인 필요 안내 화면 — 기존 유지.

## 10. 리스크 및 검증 방법

- 대규모 JSX 리라이트라 회귀 위험이 있다. 프론트 자동 테스트가 없는 프로젝트이므로, 구현 완료 후 `npm run build` 통과 + 실제 로그인해서 그룹 필터링/검색/정렬/체크박스 선택삭제/드로워 열고닫기/전체 갱신/대량 등록/내보내기까지 한 번씩 수동으로 눌러보는 검증이 필요하다.
- 백엔드 변경(8절)은 기존 `exportSnapshots`와 같은 패턴의 조회 로직 추가라 위험은 낮지만, `server/services/rankTrackerService.test.js` 관련 기존 테스트가 있다면 통과하는지 확인한다.
- "5위 내 노출" 판정 기준은 이미 백엔드에서 `status` 컬럼으로 계산되어 있음(`ranked` && `rank <= 5` → 사실 status가 이미 상위 5위 판정을 반영하고 있어 `status === 'ranked'`만 확인하면 됨, `formatRankStatus`의 기존 주석 참고).
